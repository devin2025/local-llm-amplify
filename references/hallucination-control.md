# 幻觉抑制

> 本地小模型的幻觉率是它们最致命的短板。参数调优救不了幻觉，
> 但**流程设计能**。这一份讲的是怎么用工程手段把幻觉压下去。

---

## 一、小模型为什么更容易幻觉

不是因为"知识少"这么简单。三个机制：

1. **概率补全压过了事实检索**。模型在"生成一个看起来合理的续写"和
   "回忆一个真实事实"之间，前者概率更高时它一定选前者。它无法区分
   "我记得"和"我编得像"。
2. **缺乏"我不知道"这个选项的训练**。多数模型被训练成必须给答案。
3. **上下文一长，约束力下降**。你在开头说"没有依据不要编"，
   到 20k tokens 之后这句话已经不管用了。

**推论**：靠"请务必准确"这类提示词是没用的。要靠结构和流程。

---

## 二、六条硬规则

### 1. 给模型一个"不知道"的出口

默认不许说不知道的模型，会硬编。必须显式授权：

```
如果资料中没有答案，直接回答："资料中没有提到。"
不要推测，不要用你的先验知识补全。
说不知道不扣分，编造是严重错误。
```

**这一条单独就能砍掉相当一部分幻觉。**

### 2. 强制引用，且引用必须可核对

```
每个事实性陈述后面必须标注来源编号 [1]。
无法标注来源的陈述，不要写。
```

如果模型知道每个输出都要被核对，它的编造率会明显下降。

配合 RAG 时，检索数量控制在 3–5 个 chunk（见 context-engineering.md）。
喂太多反而增加幻觉——模型会从无关 chunk 里"联想"出错误结论。

### 3. 分离"回忆"和"推理"

让模型先列出它确认知道的事实，再基于这些事实推理：

```
第一步：列出你确信知道的、与问题相关的事实。每条标注把握程度（确定/较确定/推测）。
第二步：只基于第一步中标为"确定"的事实进行推理。
第三步：给出结论。
```

模型在"列事实"时的编造率明显低于"直接给结论"时。

### 4. 一致性交叉检验

同一个问题，换措辞问 2–3 次，比对答案。

```bash
python llm.py --user "X 的作者是谁" --profile judge --seed 1
python llm.py --user "谁写了 X"    --profile judge --seed 2
```

答案不一致 = 高度可疑。**这是最便宜的幻觉探测器**，成本只有 2–3 次调用。

### 5. 让模型自己找矛盾

```
在给出最终答案前，检查以下三点：
1. 我的回答里有没有任何一条是无法从给定资料推出的？
2. 有没有和已知事实冲突的地方？
3. 我有没有在用"一般来说""通常是"来掩盖不确定？
列出发现的问题，然后修正。
```

注意：自检能抓到的主要是**内部矛盾**和**越界推断**，
抓不到**事实错误**（模型不知道自己记错了）。别高估这一招。

### 6. 低温 + 低 top_p

| 参数 | 幻觉影响 |
|---|---|
| temperature ↑ | 幻觉率 ↑（探索越多，越容易偏离事实轨道） |
| top_p ↑ | 幻觉率 ↑ |
| min_p ↑ | 幻觉率 ↓（砍掉长尾 token，很多幻觉就藏在长尾里） |

事实性问答推荐：`temperature 0.1–0.3, top_p 0.7–0.85, min_p 0.05`

**但别迷信这个。** 温度降到 0，模型仍会 confidently 地重复一个错误的记忆。
温度只影响采样多样性，不影响记忆真伪。

## 三、按任务类型的处理

| 任务 | 主要幻觉风险 | 对策 |
|---|---|---|
| 事实问答 | 编造事件/数据 | 强制引用 + 允许说不知道 |
| RAG | 从无关 chunk 联想 | 限 3–5 chunk + 强制引用 |
| 代码 | 虚构不存在的 API | 强制跑测试；API 必须来自给定文档 |
| 数学 | 计算错误伪装成推理 | 分步 + 投票 + 能算的交给 Python |
| 写作 | 虚构细节充数 | 明确哪些信息由用户提供，不得补充 |
| 翻译 | 添加原文没有的信息 | 要求逐句对照，禁止增译 |

### 代码任务的特殊一招

```
只使用下面文档中出现的 API。
如果需要的 API 不在文档里，说明"文档未提供"，不要凭记忆写。
```

本地代码模型虚构 API 是最高频的失败模式，这一条几乎能根治。

### 数学/计算的特殊一招

**不要让模型心算。** 让它写 Python，然后执行。

```
先写出求解这个计算的 Python 代码，我会执行它并返回结果。
不要自己算。
```

模型算 1234 × 5678 会错，写 `print(1234*5678)` 然后执行，永远不会错。
能外挂工具的计算，一律外挂。

## 四、RAG 场景的幻觉控制

标准做法，按顺序做：

1. **检索**：3–5 个最相关 chunk
2. **重排**：把最相关的放**开头和结尾**，最弱的放中间
3. **标注**：每个 chunk 带 `[1] [2] [3]` 编号
4. **约束**：
   ```
   只使用下面资料中的信息。
   每条结论后标注来源编号。
   资料中没有的，回答"资料中没有提到"。
   不要用你的背景知识补充。
   ```
5. **校验**：用投票或交叉检验确认关键结论

### 检索质量 >> 检索数量

一个相关的 chunk 加四个无关 chunk，效果**差于**只给那一个相关的。
无关内容不只是浪费，它会主动诱导模型跑偏。

## 五、给 agent 的特别提醒

Hermes / deepseek-harness 这类 agent 有个特殊风险：**错误会累积**。

第一轮的幻觉会成为第二轮的输入事实，第三轮再基于它推理，
到第五轮整个任务已经建立在一个虚构的前提上，而且模型会越来越"确信"。

对策：

1. **关键事实要回溯验证**。每 3–5 步，回到原始资料核对一次核心前提。
2. **工具结果优先于模型记忆**。执行结果、文件内容、API 返回值，
   一律以工具为准，模型记忆只做补充。
3. **失败时不重试同一个 prompt**。换个措辞或拆细粒度，
   同一个 prompt 在同一上下文里重复提交会沿同一条错误路径走。
4. **错误信息要隔离**。出错时的 traceback 处理完就丢掉，
   别留在上下文里污染后续推理。
5. **长任务开新上下文**。历史越长，前面埋的隐患越难清除。

## 六、自检清单

交付前快速过一遍：

- [ ] 有没有给模型"说不知道"的出口？
- [ ] 事实性陈述是否强制引用？
- [ ] 关键结论做过交叉检验吗？
- [ ] 能外挂工具验证的（计算/代码/检索），外挂了吗？
- [ ] 检索 chunk 数是不是在 3–5 之间？
- [ ] 关键约束有没有在 prompt 末尾重申一次？
- [ ] 温度是不是偏高了？
