# 推理时计算扩展（Test-time Compute）

> 核心思想：**模型一次生成的答案，不等于它能力的上限。**
> 把一次"直接吐答案"，换成"生成多个候选 + 验证 + 筛选"，用更多推理时间换准确率。
>
> 这是本地小模型对抗大模型的唯一有效杠杆。权重比不过，就把计算量堆上去。

---

## 一、三个层级，按性价比排序

| 层级 | 手段 | 成本 | 收益 | 适用 |
|---|---|---|---|---|
| L1 | 更好的单次提示（few-shot / CoT / 格式约束） | 1x | 中 | 所有任务 |
| L2 | 采样聚合（self-consistency 投票 / best-of-n） | 3–10x | **高** | 有唯一正确答案的任务 |
| L3 | 迭代修正（plan→solve→critique→revise） | 3–5x | 高 | 复杂多步任务 |

**先做 L1，再上 L2，最后 L3。** 跳过 L1 直接上 L3 是浪费。

---

## 二、L2：Self-consistency 投票

### 原理

同一个问题，高温采样 N 次 → 得到 N 个候选 → 抽取答案 → 归一化 → 聚类 → 多数胜出。

同一个模型、同样的权重，只因为"多想了几遍并且采纳多数意见"，
数学题正确率能提升一大截。这是目前性价比最高的一招。

### 关键：采样必须够多样

**低温采样做投票 = 同一个答案抄 N 遍 = 白烧算力。**

| 场景 | 温度 | 说明 |
|---|---|---|
| 投票采样 | 0.7–0.9 | 制造差异 |
| 单次求解 | 0.2–0.4 | 追求稳定 |

这就是为什么 `profiles.json` 里 `math_logic` 和 `math_logic_vote` 是两个档位。

### N 取多少

```
N=1  → 基线
N=3  → 吃掉约一半的收益
N=5  → 甜点，性价比最高
N=8  → 收益接近饱和
N>10 → 边际收益极小，纯烧时间
```

### 置信度怎么用

`vote.py` 输出的 `confidence = 最高票数 / 有效候选数`：

| 置信度 | 解读 | 动作 |
|---|---|---|
| ≥ 0.7 | 答案可靠 | 直接用 |
| 0.5–0.7 | 可用，但有分歧 | 人工扫一眼，或加 `--judge` |
| < 0.5 | 模型自己都不确定 | **别信**。提高 N、改提示词、或换策略 |

### 什么时候不要用投票

- **创意写作 / 视频脚本**：要的是多样性，不是收敛。投票会把最平庸的那个答案选出来。
- **没有唯一答案的任务**：投票毫无意义。
- **简单事实问答**：杀鸡用牛刀，L1 的 few-shot 就够了。

### 用法

```bash
python vote.py --task "..." --n 8 --profile math_logic_vote --extract boxed
python vote.py --task-file req.txt --n 6 --extract code --verify tests.py
python vote.py --task "..." --n 5 --judge          # 平票时让模型裁决
```

代码任务加 `--verify` 是**质变**：先用测试过滤掉跑不通的候选，
再在通过者里投票。比单纯投票强得多。

## 三、L3：迭代修正流水线

### 为什么有效

模型一次性从头生成到尾时：前面犯的错会一路带到底，而且它没有余力回头检查。

拆成四步之后：
1. 每步上下文更短，注意力不被稀释
2. 批判阶段用**低温裁判档**，等于给模型一次"跳出自己"的机会
3. 修订阶段只看方案 + 意见，不看原始错误输出，避免被自己带偏

### 四阶段

```
规划 plan      → 低温。确定路径、列出边界条件。不产出最终答案。
求解 solve     → 按路径执行。
批判 critique  → 低温裁判档（temp 0.1）。找错，输出 PASS/FAIL。
修订 revise    → 根据意见重做。
```

`--rounds` 控制批判-修订循环次数。**1–2 轮足够**，超过 3 轮收益递减，
而且模型会开始"为了改而改"。

### 关键设计：批判阶段必须用低温

用高温让模型批判自己的输出，它会：自我辩护、敷衍说"挺好的"、
或者瞎改一通。裁判档（temp 0.1, top_p 0.7, top_k 10）是必须的。

### 代码任务加验证器

```bash
python pipeline.py --mode code --task-file req.txt --verify tests.py --rounds 2
```

每轮修订后真跑一遍测试。**能跑测试的代码任务，永远不要靠模型自评。**
执行结果比任何裁判都可靠。

### 什么时候不要用流水线

- 短问答 / 简单分类：过度工程，反而更慢更差
- 纯创意任务的一次性灵感：批判阶段会把锐度磨平
  （但"批判 + 修订"对创意任务的**打磨**阶段仍然有效）

## 四、Best-of-N + 验证器

投票的变体。不是数票数，而是**用可靠的验证器给每个候选打分，取最高分**。

| 任务 | 验证器 | 可靠性 |
|---|---|---|
| 代码 | 执行测试 | ★★★★★ 客观 |
| 数学 | 抽取答案比对 | ★★★★☆ |
| 格式 | JSON schema / 正则 | ★★★★★ 客观 |
| 事实 | 检索对照 | ★★★☆☆ |
| 写作 | 模型打分（LLM judge） | ★★☆☆☆ 主观 |

**优先级：客观验证器 >> 模型自评。** 有测试就跑测试，别问模型"你觉得对吗"。

LLM judge 的已知偏差，必须知道：
- **偏好长答案**：啰嗦的候选容易得高分
- **偏好同族模型**：用 Qwen 评 Qwen 会虚高
- **位置偏差**：倾向选第一个或最后一个候选
- **分数压缩**：总打 7–8 分，区分度低

缓解：要求先输出评分理由再打分；把候选顺序打乱；用 rubric 而不是笼统"打分"。

## 五、MoA：多模型编排

Mixture of Agents。让多个模型分别产出，再让一个模型综合。

```
Proposer A ─┐
Proposer B ─┼→ Aggregator → 最终答案
Proposer C ─┘
```

在你这套配置上的落地方式：

- **双服务实例**：8080 跑 Qwen3-30B-A3B，8081 跑 Qwen2.5-Coder-14B
- 通用任务：30B 出草稿，30B 低温档批判
- 代码任务：Coder-14B 出代码，30B 批判代码逻辑
- **交叉批判比自我批判有效得多**——同一个模型很难发现自己的思维盲点

用 `--compare-endpoint` 在 `bench.py` 里量化对比，别凭感觉。

## 六、成本收益速查

| 手段 | 相对耗时 | 典型提升 | 优先级 |
|---|---|---|---|
| few-shot 示例 | 1.1x | +10–30% | 1 |
| 参数调优 | 1x | +5–20% | 2 |
| min_p / DRY | 1x | +5–15% | 3 |
| 四阶段流水线 | 3–5x | +15–40%（代码/推理） | 4 |
| 投票 N=5 | 5x | +10–25%（有唯一答案） | 5 |
| 投票 + 测试过滤 | 5x | +20–40%（代码） | 5 |
| MoA 多模型 | 3–6x | +10–20% | 6 |

数字是经验值，不是承诺。**用 `bench.py` 在你自己的题集上测，才是真的。**

## 七、决策流程

```
有唯一正确答案吗？
├─ 是 → 能客观验证吗（测试/比对）？
│        ├─ 能 → pipeline --verify 或 vote --verify   ← 最强
│        └─ 不能 → vote.py（N=5~8，看置信度）
└─ 否 → 多步复杂任务吗？
         ├─ 是 → pipeline.py（--mode write/script，1–2 轮）
         └─ 否 → L1 就够：few-shot + 参数调优，别过度工程
```
