# 上下文工程

> 本地模型最大的瓶颈不是知识，是**注意力预算**。30B 以下尤其明显：
> 上下文一长就顾头不顾尾。这一层做对，等于给模型换了个更大的脑子。

---

## 一、Lost in the Middle（中间迷失）

模型对长上下文的注意力呈 **U 型**：开头和结尾记得牢，中间大段被严重稀释。
塞 20k tokens 资料进去，中间那 15k 基本等于没喂。

### 对策：三段式布局

```
[开头]  任务指令 + 角色设定 + 硬约束       ← 高注意力区
[中间]  参考资料 / 背景文档 / 历史记录       ← 低注意力区，放最不重要的
[结尾]  重申关键约束 + 输出格式 + 问题本身   ← 高注意力区
```

模板：

```xml
<instructions>
你是……
硬约束：
- 只输出代码，不要解释
- 必须处理空输入
</instructions>

<document>
……资料放这里……
</document>

<reminder>
再次确认：只输出代码，不要解释。必须处理空输入。
现在开始。
</reminder>
```

**把最重要的约束写两遍不是啰嗦，是对抗注意力衰减。实测有效。**

---

## 二、系统提示词会衰减

长对话中 system 里的指令遵循度持续下降，本地小模型的通病。

对策：
- 关键约束写进 user 消息，不要只写进 system
- 长任务开新会话，别在一串历史里硬撑
- 每 N 轮重新注入一次核心约束

---

## 三、信息密度：删比加重要

最常见的错误是"把所有东西都塞进去"。这是负优化。

### 删

| 删掉 | 理由 |
|---|---|
| 客套话 | 零信息，纯占上下文 |
| 重复的指令 | 同一条说三遍，只有最后一遍有效 |
| 无关背景 | 注意力是稀缺资源 |
| 早期错误尝试 | 会污染后续输出 |

### 加

| 加上 | 理由 |
|---|---|
| 2–4 个 few-shot 示例 | **对小模型提升最大的单项改动** |
| 明确的输出格式 | 结构化输出显著提升可用率 |
| 反例 | 小模型对反面示例的响应有时比正面指令更强 |
| 具体评判标准 | "写得好"没用，"每段必须有一个具体物件"有用 |

---

## 四、Few-shot：最该用、最常被跳过的一招

零样本裸问一个 14B，和给 3 个示例之后再问，差距经常是决定性的。
几乎零成本，收益排在所有技巧前三。

```xml
<examples>
<example>
<input>把「他很高兴」改成有画面感的句子</input>
<output>他把手机举过头顶，在客厅里转了半圈。</output>
</example>
<example>
<input>把「她很紧张」改成有画面感的句子</input>
<output>她把纸杯捏成了一个月牙。</output>
</example>
</examples>
```

三条硬要求：

1. **格式必须和期望输出完全一致**——模型模仿的是格式，不只是内容
2. **示例质量要高**——给烂例子等于教它输出烂东西
3. **示例之间要有差异**——三个同风格例子会让输出僵化

数量：2–4 个是甜点。超过 6 个收益递减且挤占上下文。

## 五、输出格式约束

本地模型最容易犯的错：让它输出 JSON，它先来一段"好的，这是您要的 JSON："
然后才开始。在自动化流程里是致命的。

### 三个手段，按强度排序

**1. 提示词（最弱，但通用）**

```
只输出一个 JSON 对象。不要任何前言、解释、markdown 代码块包裹。
第一行就是 {，最后一行就是 }。
```

**2. response_format（中，API 支持时）**

```json
{"response_format": {"type": "json_object"}}
```

llama.cpp 和 vLLM 支持。注意：仍需在提示词里描述 schema，
`json_object` 只保证是合法 JSON，不保证字段。

**3. GBNF grammar / JSON schema（最强，llama.cpp 专属）**

```bash
llama-server -m model.gguf --json-schema '{"type":"object","properties":{...}}'
```

grammar 约束是在解码层面硬截断 token 候选，**输出 100% 合法**。
代价：会增加一点延迟，且极复杂的 schema 可能让模型"卡住"。

对 agent 场景（Hermes / deepseek-harness），**能用 grammar 就用 grammar**。
工具调用格式错误是 agent 流水线最常见的失败原因，这一招直接根治。

## 六、上下文隔离：别让子任务互相污染

一次性让模型做完 5 件事，它会：遗漏第 3 件、把第 1 件的错误带进第 4 件、
在第 5 件上因为上下文太长而敷衍。

**对策：拆。** 每个子任务独立上下文。

| 模式 | 适用 |
|---|---|
| Map-Reduce | 每块独立处理，最后汇总（长文摘要、批量翻译） |
| 流水线 | 输出作为下一段的输入（`pipeline.py` 就是这个） |
| 分治 | 大问题拆成独立小问题，各自求解后合并 |

`pipeline.py` 的四阶段设计不只是"多想几步"，更重要的是**每个阶段的上下文
只包含该阶段需要的东西**。批判阶段看不到规划阶段的废话，修订阶段看不到
原始的错误输出。

## 七、RAG：喂多少才对

| 检索数量 | 效果 |
|---|---|
| 1–2 chunks | 可能漏掉关键信息 |
| **3–5 chunks** | **甜点区** |
| 6–10 chunks | 开始稀释注意力，正确率反降 |
| 10+ | 明显劣化，中间的内容被完全忽略 |

**宁可检索质量高 + 数量少，不要检索质量低 + 数量多。**

### 强制引用

```
回答时每个事实性陈述后必须标注来源编号，格式 [1]。
没有来源支撑的内容不要写。
如果资料里没有答案，直接说"资料中没有提到"，不要推测。
```

这一条同时解决幻觉和可追溯性。

## 八、给 agent 的注意事项

如果读这份文档的是 Hermes / deepseek-harness 这类 agent：

1. **你的 system prompt 正在被同一个本地模型处理。** 每一句废话都在消耗
   你自己的注意力预算。写 prompt 时用本文档的规则要求自己。
2. **工具返回结果不要全量塞回上下文。** 大文件先摘要或裁剪，只回传相关部分。
3. **长任务主动开新的子上下文。** 不要让历史无限增长。
4. **错误消息要结构化。** 模型看到一大段 traceback 会丢掉前面的任务目标。
   提取关键行，格式：`错误类型: 位置: 原因`。
5. **多轮失败后换个策略，别重试同一个 prompt。** 同一个 prompt 在同一个上下文里
   重复提交，模型会沿着同一条错误路径走。改措辞、改参数、或清空历史重来。
